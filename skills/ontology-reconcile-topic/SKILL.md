Use for pixlnd ontology decision reconciliation, not gameplay implementation. Follow repository instructions and current owner direction; preserve the requested skill name `ontology-reconcile-topic`. ## Recording routes
`docs/ROADMAP/todo_decide.md` contains unresolved game choices only. Remove an entry when resolved; delete the file when empty. Do not retain completed-item indexes or parallel decision/finding histories there, including owner answers, approval/refusal explanations, application history, reviews, commands, logs, commits, publication instructions or execution narratives.

Follow [current recording routes](../record-impactful-decision/recording-guidance.md): canonical
ontology owns gameplay and functional requirements; only nontrivial technical choices warrant

implementation or research authority.

## Handoff
`docs/HANDOFF.md` is pending-only: unfinished work, next action, active authority/blockers and
references needed to resume. Drop handled points once current rules and qualifications have canonical homes and necessary
receipts/failed-check caveats are retained in managed evidence. Follow the recording routes above;
do not copy authority exchanges or history into repository records. Implementation debt belongs
in `todo_implement.md`, and reusable workflow rules in their relevant skills. Reference pending
queues/backlogs rather than copying them; recorded documentation is not implemented gameplay.
A complete/terminated project with no continuation needs has an empty (zero-byte) handoff,
not a title or completion summary. Never restore completed history into an empty handoff.
Do not edit HANDOFF while another agent owns it; defer its update to that writer.

## Context budget
- Check reported context usage before broad reads, question presentation, each item and review. Prepare and present the answer batch at **~60% context maximum**, including room for the question output. Use bounded delegation and retained evidence; reserve the rest for answers, recording, review and publication. If already above the asking ceiling, checkpoint rather than expand the batch.
- **Begin handing off at ~85%**, or earlier if the next item/review would consume the reserve. Stop research, new questions and new item starts; finish only the active coherent checkpoint. Do not depend on automatic compaction to complete the session. If usage cannot be measured, say so and checkpoint conservatively rather than invent a percentage.
- Preserve all approved-but-unhandled items in `./docs/todo_handle_reconciled_items.md` before recording begins and at handoff. This file is pending-only: remove handled entries after verified recording/commit; delete the file when empty. Context-triggered handoff follows step 8: commit the checkpoint, push the authorized branch, verify publication and STOP. Explicit owner restrictions on publication still take precedence.

## Procedure
1. Establish authority: inspect the actual Git branch, HEAD, worktree and upstream. Read the required bootstrap documents, canonical ontology, decision ledger, `./docs/todo_handle_reconciled_items.md` if present, lessons/protocol and handoff. Prefer current files and explicit owner instructions over stale summaries. Preserve unrelated edits and settled decisions.
2. Resume the unfinished topic/items, handling pending selected decisions before new questions. Distinguish unanswered proposals, approved-but-unrecorded decisions, recorded policies and deferred implementation. Do not treat implementation debt as a missing design decision.
3. Read the topic's definitions, relations, constraints, instance data and relevant consumers. Apply the source-retrieval and quantitative checks below when relevant, before recommending or recording a rule. Present one batch of five distinct known authorized unanswered items, allowing fewer only for the genuine final remainder of the finite authorized frontier or context reserve. Retain all remaining questions for later batches; never invent filler or expand authority. For each, separate settled facts from **Recommended**, explain the finished player experience with an example/tradeoff, and use the exact heading 'Approval versus Refusing'. For a saved decision, show **Previously selected** with amendments folded into the current selected rule/option and pending status instead of treating it as a new recommendation or requiring reapproval. Ask only genuinely unresolved numbered questions; wait for their answers.
4. Immediately persist unhandled selections in `./docs/todo_handle_reconciled_items.md` (create only when needed): topic/item number, selected current rule/option with amendments folded in, approval versus application status, dependencies and documentation/implementation boundary. Exact answers and original dialogue stay in managed evidence under the recording guidance. This is a decision/application queue, not a second canonical ontology. Check answers against each other and settled rules. A question is not rejection; refusal does not approve the opposite. Clarify real ambiguities/conflicts in a follow-up batch within budget; preserve approved principles and hold dependent application rather than invent defaults. Never reopen settled choices or manufacture speculative questions.
5. Require explicit recording authority and exclusive worktree ownership. For an authorized effective-rule change, update canonical ontology first with necessary relations/constraints; use the loaded decision helper for classification and technical-record review, not gameplay history. For source precision, use the loaded finding helper without changing the effective rule. Keep `todo_decide.md` limited to unresolved choices; remove resolved entries rather than leaving completed-item pointers. Track deferrals only in the implementation backlog. Approval of ontology documentation does NOT authorize gameplay, labels, tests, loader/validator changes or behavior-changing JSON. Obtain separate implementation permission; then use the repository's implementation routing rather than this walkthrough.
6. For EACH substantive reconciled item: inspect scope and semantic fidelity; run /simplify then ponytail-review and apply appropriate adjustments; run git diff --check and the repository's bounded validator/relevant checks; create one separately scoped conventional commit. Stage only intended files; routine receipts alone require no knowledge record or invented commit. After recording, checks, required review and the item commit are verified, retain raw authority plus sourcing/review/commit receipts in managed evidence and effective amendments in canonical rules; remove the resolved question from `docs/ROADMAP/todo_decide.md` without leaving a completed-item pointer, then remove its entry from `./docs/todo_handle_reconciled_items.md`. Keep partially applied or review-pending selections queued. Delete the queue file when no unhandled entry remains; do not keep completed-item history there. Keep item-to-commit evidence. Use fresh read-only review for substantial batches and resolve findings without overriding owner decisions.
7. If delegated, keep one writer per worktree and bind exact approvals to its task. When later approvals arrive, update the brief and notify the same writer. A queued steering receipt is not compliance: inspect completed output, actual diffs, numbered decisions, commits and final verification. Follow the installed subagent protocol; infrastructure failures are blockers, not permission to switch execution modes.
8. When a topic is fully reconciled, move to the next topic only if not stopped and the context budget allows. On explicit HANDOFF or the ~85% trigger, follow the Handoff contract above: retain only unfinished continuation and necessary references; remove handled points after current rules/qualifications have canonical homes and required receipts are retained in managed evidence. Update `./docs/todo_handle_reconciled_items.md` with every approved-but-unhandled item and its current Previously selected option with amendments folded in, status, dependencies and documentation/implementation boundary; remove handled entries and delete the queue if empty. Name pending items as the next work before any new topic. Commit authorized handoff and pending queue changes (including deletion), push only the authorized branch, verify fresh remote/upstream/local equality and clean worktree, then STOP the walkthrough. If pushing fails, report it without claiming publication or force-pushing. A separately requested post-handoff task may proceed.

## Source retrieval
- For external source research, load `playwright-cli` and try Playwright before shell retrieval. Pause for owner-performed manual authentication/access checks; never request credentials or automate a bypass. Shell fallback is for technical browser unavailability, not access denial. Stop on unexpected redirects, error/challenge pages or unusable content; retain failure evidence instead of retrying around it.
- If the owner requests a browser switch, use another already-installed browser rather than repeatedly tuning the broken one. Switching grants neither bypass permission nor authority to resume stopped research.
- Before restarting Firefox, confirm the owner's intended logged-in profile; neither a process's `-P` argument nor a default-profile flag establishes that intent. On mismatch, stop and ask. Verify the chosen profile's actual process/lock ownership; act only on that profile and preserve unrelated windows. Never delete a lock without proving no live process owns it and obtaining authorization for removal.
- For retained raw-revision/derived-text comparisons, check identity, revision, timestamp and authoritative content separately. On mismatch, preserve the failed assertion and compare exact bytes in the permitted local diagnostic scope. Record a proven derivative transformation (such as one added terminal LF) without normalizing the raw source or claiming byte equality. A substantive content or identity mismatch holds the candidate; a documented derivative-only difference does not invalidate matching authoritative raw content.
## Quantitative decisions
- Separate aggregate bonus from each contributor's share, and retroactive equal sharing from acquisition-order rewards. Simplify formulas to expose cancelled tunables; check zero, first and large counts, units and any required monotonic totals. Flag conflicts with existing floors; do not invent constants, clamps or extensions to other item kinds.
- A percentage reduction leaves a remaining cost, not an exemption. Name the base being reduced; distinguish percentages from percentage points. Stacking order and additive versus remaining-cost multiplication need their own approved rule, not an inference from the percentage.
- For encounter chances, state the eligible population/denominator and clarify any unresolved roll unit or independence. A conditional percentage does not select arbitrary species weights, habitat changes or encounter frequency.
- For approved percentage-based damage gains, use actual HP removed relative to maximum HP, not attempted damage or remaining HP. Check zero removal, overkill, fractional gains and equal-percentage hits at different HP scales. Examples test the approved rule; they do not approve new balance values.

## Pitfalls
- Handoff, silence, a green validator and blanket approval of another topic do not approve unanswered proposals. Conversely, a saved explicit approval is not unanswered merely because canonical recording is pending; do not ask the owner to decide it again.
- The 60% asking ceiling and 85% handoff trigger are reserve boundaries, not targets to fill. Begin earlier when necessary; never lose approvals to context overflow.
- Validation of loaded data does not prove natural-language consistency or runtime compliance. State what was actually tested; do not reuse old logs as fresh proof.
- Obsolete checked-in values do not overturn the latest approved canonical rule. Distinguish stale data from missing enforcement; generic advice to fit a model to instances is not authority to reopen settled mechanics.
- Do not push before explicit authorization, merge, force-push, rewrite history, or commit unrelated user changes. Respect the repository's Git conventions.
- Keep only unhandled selections in `./docs/todo_handle_reconciled_items.md` and routine receipts/scratch evidence outside the repo; follow the Recording routes above. Standing source precision authority never authorizes gameplay or labels. Do not create parallel specs or bake domain decisions, current topics or commit hashes into this skill.
- Pixlnd entry points: read docs/HANDOFF.md, ontology/README.md + ontology/domain/index.dsl, game/README.md, docs/lessons.md and the unresolved choices in docs/ROADMAP/todo_decide.md if present. Track deferred runtime in docs/ROADMAP/todo_implement.md. Validate with timeout 150 nix develop -c godot --headless -s ontology/validate.gd. Obtain all settled and permanently excluded game rules from the current canonical files.
